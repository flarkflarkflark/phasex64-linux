# v0.1.12 design: asynchronous live codec apply with timeline continuity

Status: **proposal only, awaiting approval; no driver changes or build**.
Design branch: `design/v0.1.12`, based directly on main `9f1482f`.
Diagnostic evidence: `diag/live-resync`, driver `d5e9c86`, report `92d6e00`
(`analysis/live-resync-step1b.md` on that branch). Do not merge the diagnostic
implementation wholesale. Hardware validation was on 2026-10-15; design dated
2026-10-16. PipeWire may remain stopped while the user tests mode 4 in REAPER.

## 1. Outcome and non-negotiable acceptance

Mode 3 (capture + feedback stopped, playback endpoint running) failed both
Direct transitions: SET_CUR/GET_CUR returned -EPIPE. Mode 4 (all audio URBs
stopped, complete codec/rate/status restart) passed both transitions, with
316/312 ms restart durations and genuine capture 1/2 ms after resubmit.
The approximately 315 ms gap is comparable to Windows' approximately 330 ms.
This establishes a working Linux sequence, not that stopping playback alone
explains it or that Windows uses precisely the same sequence.

The diagnostic freezes ALSA pointers during that interval. The user confirmed
in REAPER that recording survives at the normal buffer without EIO/XRUN, but
approximately 0.3 s is **missing** at each toggle; later audio shifts earlier.
Thus a successful mixer apply is not a successful production implementation.

v0.1.12 must preserve elapsed time, not uninterrupted sound:

- Every live toggle produces a silent capture interval covering the measured
  outage; subsequent audio stays at its original timeline position.
- Playback advances during the outage, discarding the corresponding audio,
  rather than playing it late after recovery. Physical playback has a dropout.
- REAPER must survive at periods of 128, 256 and 512 frames, with both two and
  three periods per buffer, without gap-induced EIO/XRUN or pointer stalls.
- A ten-minute recording with five toggles must differ from independently
  measured wall-clock duration by **less than one configured period**.
  No per-toggle rounding budget: five small timing errors must not accumulate.
- A planned restart does not call `snd_pcm_stop*`, change `s->active`, reset
  the ALSA hwptr, or change the PCM rate. Actual stop/disconnect and unrecoverable
  failures remain real lifecycle events; they must not be hidden by endless silence.

Apply all codec-backed controls, not just Direct 1/2: Direct 1/2 and 3/4,
PCM 1/2 and 3/4, Direct Mono 1/2, PCM Mono on both pairs, Capture Source 1/2
and 3/4, and Sound Module 3/4 (same codec register family). Preserve the
existing Mic + Direct prerequisite for Direct Mono 1/2, including collateral
control notifications. Codec 1's corresponding bit means Sound Module, not Mono.

When transport is running, route changes through the asynchronous full restart.
With transport idle, retain existing idle codec writes/shadow semantics and
normal next-start replay; do not start audio just to apply a control. A running
transport with no active ALSA direction still needs hardware serialization but
no synthetic PCM frames. RIAA software switches need no hardware restart;
clock/rate changes and MIDI are not added to this live-control feature.

## 3. Desired state, workqueue and coalescing

Use one per-device work item on an ordered process-context workqueue. Both it
and the watchdog take `px->mutex` for hardware operations. Only one hardware
restart/recovery transaction may exist, including the post-submit wait for
genuine completions. Normal start must use the same ownership protocol.

Introduce a short-held desired-state spinlock, separate from `px->mutex`:

- `put` validates the value and interlocks, atomically changes the complete
  desired codec snapshot, increments `desired_gen`, and queues work if permitted.
  It returns 1 for a logical change, 0 for no change, negative for validation or
  known device removal. There is no streaming USB transfer or sleep in `put`.
- `get` returns desired state under that short lock, so the panel stays responsive.
  `put` success means accepted for application, not confirmed in hardware.
- Keep desired, transaction snapshot and successfully applied generation separate.
  The current USB helper also writes `px->codec`; using it unchanged would allow
  an older worker snapshot to overwrite a newer user choice. Split that behavior.
- Publish queue ownership/dirty state under the same lock as shadow changes.
  At worker exit, atomically check for newer work before releasing ownership.
  Queue return values alone are not a last-wins protocol: test the exit/put race.
- The worker holds `px->mutex` through the USB sequence, but only briefly takes
  the desired lock to snapshot/check generations. Puts must not wait behind the
  315 ms mutex hold, otherwise asynchronous coalescing would be ineffective.
- Idle writes recheck transport/lifecycle after acquiring `px->mutex`, snapshot
  current desired state, and use the streaming route if a start won the race.
  Normal start likewise snapshots the latest desired state. Never hold the
  desired spinlock while waiting for a mutex, doing USB I/O or notifying ALSA.

Coalesce the burst into one endpoint stop/resubmit cycle: after the initial
settle, apply the latest full six-register snapshot, not a queue of individual
button edges. Recheck `desired_gen` after control writes and immediately before
resubmit. If it changed, stay quiescent and repeat the codec/rate/status commit
for the latest snapshot, including required settles; the silence timer continues.
Intermediate states need not become audible. Bound repeated commits so a control
flood cannot hold the device idle indefinitely; log incomplete/pending generations.

There is a necessary commit fence: under the desired lock, mark the stable
snapshot RESUMING before submitting URBs. Changes accepted after this fence
belong to the next transaction, even if the first genuine capture is still
1–2 ms away. They must not be lost. The practical guarantee is one restart for
changes before this fence; an absolute guarantee for *every* change until first
audio would require freezing control acceptance or indefinitely delaying resume.
This boundary and a bounded control-flood policy need approval (section 10).

## 4. Hardware transaction and watchdog

State progression:

`IDLE/RUNNING -> QUIESCING -> APPLYING -> RESUMING -> RUNNING`

Stop, disconnect or suspend may invalidate any transaction generation. Capture
and playback also have separate TIMER/URB ownership during RESUMING, because
one endpoint's recovery does not prove the other's.

1. Under `px->mutex`, recheck running, lifecycle gate and generation. Publish
   `cap_live_restart_pending` **before any kill**, and transfer active PCM frame
   ownership to the gap clock under each stream lock. Block old-generation
   callbacks from requeueing. Arm silence/discard timing before sleeping.
2. Kill all audio URBs using the shared helper. Do not call the existing full
   `px_stop_streaming()` as-is: it changes lifecycle and synchronously cancels
   the watchdog. Keep ALSA substreams RUNNING and do not reset their positions.
3. Wait the validated pre-codec settle. Replay all six codec writes from the
   transaction snapshot, irrespective of a legacy `codec_resync=0` override:
   complete replay is part of live apply's contract. Keep default codec resync on.
4. Reuse common start helpers for SET_CUR capture/playback/capture, GET_CUR
   index 0 verification, unconditional cached STATUS write, 40 ms status settle,
   90 ms clear-halt settle, and clear_halt 0x86. No live STATUS read. Retain
   requested rate/clock; a failed verify or wrong rate is not successful apply.
5. Finish generation/coalescing checks; commit applied source/RIAA state before
   new data can be decoded. Reset feedback FIFO/rate scheduling state safely.
   Immediately before resubmit, refresh the watchdog deadline (initially the
   diagnostic's 1000 ms) and recheck running, lifecycle and transaction generation.
6. Submit in the actual main/mode-4 order: **capture, feedback, playback**.
   Do not silently substitute the feedback-first order from earlier experiments.
   The gap clock continues until each direction has a valid ownership handoff.
   Release the hardware mutex after submissions; do not hold it while waiting
   for recovery. RESUMING still excludes another transaction. Completion of the
   handshakes makes any newer desired generation eligible for the next worker run.
7. A successful, nonzero 0x86 completion from the new submission generation
   clears capture pending and supplies genuine liveness. Zero/error completions,
   killed old URBs and synthetic silence never do. Full-frame validity is also
   required before using capture data for the timeline handoff.

Pending suppresses planned-gap watchdog escalation, not monitoring forever.
Check it again **after acquiring `px->mutex`**, since the watchdog may have
waited behind the worker using stale pre-gap timestamps. Check genuine-data
timestamps again there too. A timeout after resubmit transfers recovery ownership
to the existing watchdog through the same transaction state; no parallel restart.
Playback/feedback failures need their own detection: capture success cannot
declare a duplex restart healthy. Extend the watchdog's transaction supervision
to run during RESUMING even for playback-only use (its current early return on
inactive capture is insufficient), without enabling unrelated capture recovery
when no transport is running. Log request/applied generations, stage times,
kill/submit counts, first genuine completion, silence/discard frames and error.

Abort immediately on -ENODEV/-ESHUTDOWN in every control and submit loop, without
retry or further submissions. Other errors have a finite recovery budget and
leave applied state explicitly unconfirmed if the transaction was partial.
Production must not inherit mode 4's log-and-continue treatment of failed steps.
The worker never synchronously cancels itself. Failure cleanup uses the common
quiesce path, with terminal ALSA failure reported outside conflicting locks.

## 5. Cancellation and lock/lifetime contract

There is an existing deadlock possibility to remove, not copy: main's
`px_stop_streaming()` at 1024 calls `cancel_delayed_work_sync()` while callers
hold `px->mutex`, and `px_cap_watchdog_fn()` at 863 can be waiting for that mutex.
Process context permits sleeping, but does not make this lock dependency safe.
Adding `cancel_work_sync()` for the new mutex-taking worker there would repeat it.

Use two-phase teardown, serialized by a lifecycle gate/generation:

1. Publish stopping/disconnected/suspended and block all queue/requeue producers;
   invalidate the transaction. Trigger STOP only marks its direction inactive
   and requests cancellation using atomic-safe operations. It cannot wait.
2. From sleepable sync_stop/close/hw_free/rate-change/disconnect/suspend paths,
   call `cancel_work_sync()` and `cancel_delayed_work_sync()` **outside
   `px->mutex`, ALSA stream locks and callback spinlocks**. A worker holding the
   mutex must observe the stop request and abort; it must not await the cancelling
   thread. Gate the watchdog's current unconditional self-requeue as well.
3. Cancel/drain the relevant gap timer outside locks its callback can acquire;
   wait for existing `in_elapsed` references, then finish URB/runtime cleanup
   under the hardware mutex. Recheck generation so an older close cannot stop
   a newer prepare/start. New starts are serialized against the teardown gate.

An individual capture or playback STOP must not stop a still-active duplex peer.
Disable only that direction's timer/data ownership. Process-context cancellation
of shared work must leave transport usable for the peer: if already quiesced,
finish a serialized restore for the peer before releasing the lifecycle gate,
then requeue any newer desired state. Test close/reopen of either side mid-gap.
This peer restore is not a concurrent second restart. Last-direction stop,
disconnect and suspend do no restore/resubmit. Resume uses the normal start path.

Lock ordering: hardware mutex may briefly take desired or stream locks; desired
and stream locks are not nested with each other. No callbacks/timers take the
hardware mutex. Release driver spinlocks before `snd_pcm_period_elapsed()` and
hold an `in_elapsed` lifetime reference across it, just like existing URB paths.
Do not invoke period notifications directly from a mutex-held worker helper.
No worker waits for a callback which is itself waiting for that worker's lock.

These constraints follow the [workqueue cancellation contract](https://docs.kernel.org/core-api/workqueue.html#c.cancel_work_sync)
(including the need to exclude racing enqueues), the
[ALSA interrupt/atomicity rules](https://docs.kernel.org/sound/kernel-api/writing-an-alsa-driver.html#pcm-interrupt-handler),
and [hrtimer cancellation semantics](https://docs.kernel.org/driver-api/basics.html#c.hrtimer_cancel).

## 6. Mandatory timeline bridge

Use a CLOCK_MONOTONIC hrtimer per active PCM direction, with a common gap epoch
and independent period cadence. Separate timers avoid assuming capture and
playback have the same period size. Maintain 64-bit absolute frame counts;
derive ring hwptr by modulo only when reporting/writing the ring.

For a stream's anchored sample clock, compute target frames from absolute elapsed
nanoseconds and rate, carrying fractional-frame remainder across handoffs. Do
not repeatedly add a rounded period duration or round each 315 ms gap separately.
Schedule the next absolute period boundary, preserving partial `period_pos` at
entry. At 48 kHz, 128/256/512-frame periods are 2.667/5.333/10.667 ms; at 96 kHz,
128 frames gives only 1.333 ms. Timer work must be short, preallocated and bounded.

Capture timer: fill every due frame with zero in the existing six-channel S32_LE
ring, wrap correctly, then publish hwptr/period_pos and notify ALSA at each normal
period tick. Silence bypasses RIAA; never expose stale ring contents or filter
ring-down as the intentional gap. Playback timer: advance the corresponding
logical frame count and period notifications without sending or replaying those
samples. REAPER is woken throughout the gap, so its small ring continues to be
consumed/refilled instead of freezing for 315 ms.

On a delayed timer tick, account for elapsed frames once and notify the updated
pointer; do not emit many notifications against the same pointer to simulate
missed scheduling. A delay exceeding available buffer slack is a real overrun/
underrun, not something modulo arithmetic can hide. The requirement is no XRUN
caused by the deliberate USB gap under tested scheduling conditions, not immunity
to arbitrary CPU starvation.

### Frame ownership and handoff

Both timer and URB paths use each stream's lock and generation to claim frame
ranges exactly once. At entry, anchor to the last accounted sample timeline,
including the partial period, rather than merely starting a new timer after
`usb_kill_urb()` returns. All quiesce/kill/settle/resubmit time must be represented.
Old-generation completions cannot add audio after ownership has moved to TIMER.

On the first genuine new capture completion, establish the first usable batch's
sample interval, fill any remaining missing prefix with silence, and transfer
ownership atomically to URB. Do not first fill silence through completion time
and then append the entire batch: the batch itself spans earlier sample time,
so that would add an overlap at every toggle. Trim/discard already represented
prefix frames; carry the sub-frame phase forward. Later timers see URB ownership
and do nothing. A zero/error completion cannot take ownership. Non-synchronous
timer cancellation is optional in the callback; generation checks provide safety,
and process-context teardown performs the synchronous drain.

Capture is bulk, without per-sample hardware timestamps. A completion timestamp
minus batch duration is only an estimate of the batch's sample interval. Measure
normal transport latency/buffering and first-batch behavior using analog markers;
instrument frame counts and carry fractional correction, rather than claiming
that host arrival time is exact ADC time. If stale device-buffered frames appear
after restart, define and validate a bounded discard rule. This calibration is
a release gate for the less-than-one-period requirement, not a hidden assumption.

### Playback must distinguish queued from elapsed samples

Today `px_play_copy()` advances hwptr when filling an URB, **before completion**.
Blindly adding timer advances and doing the same four-URB prefill on resume
double-counts time/consumption, including already credited URBs killed at entry.

Proposed production accounting: keep a private reservation/copy cursor and tagged
frame ranges per URB, separate from ALSA's elapsed/presented frame cursor. Prefill
reserves data without publishing it twice; normal completions retire their ranges.
During a gap the timer retires discarded ranges at sample cadence. Cancelled
queued ranges are accounted for once as lost time, never rewound or replayed.
On resume reserve future, not already discarded, data; a genuine playback
completion transfers ownership and credits only previously unaccounted frames.
Prepared-but-inactive silence URBs must never consume application frames.

This is an intentional playback-accounting refactor, not just a timer added to
the existing fill helper. Preserve buffer-availability limits and audit ALSA
delay/timestamps against the new cursor. Exercise initial start, drain/EOF, mmap,
capture-only and duplex. Capture recovery must not switch off the playback timer
before playback itself has made a valid handoff. Neither direction may step its
public pointer backwards or acquire a fresh queue-depth offset on every restart.

## 7. RIAA and applied capture source

The pending desired source is not yet the hardware source. Until commit, decode
using the applied source's `riaa_active` state. Once the new source transaction
is committed, and before its first real capture data is accepted, publish the
applied source and reset the affected pair's RIAA state under `cap.lock`.
Retain existing reset rules for stream start and rate change. Both source enums
include Phono; validate both paths on hardware rather than assuming identical
physical routing. Mono prerequisites are part of the same desired snapshot.

Propose resetting both active RIAA pairs on any full restart too: there is no
valid filter history for the missing input interval. Keep inserted silence exactly
zero rather than processing zeros through the filter. Check the first resumed
samples for transients/clipping, and do not inadvertently enable RIAA on a
non-Phono source while an asynchronous source change is still pending.

## 8. Gap minimisation: measurements, not guessed defaults

Retain runtime `live_settle_ms` with mode **0644**, validated range 0–500 ms,
snapshot once per transaction. Initial conservative candidate is **170 ms**,
the only value validated with mode 4 so far. Production default is whichever
value passes the complete matrix with margin; do not claim 0/50/100 ms work yet.

| Stage | Sweep | Hold constant / measure |
|---|---|---|
| Pre-codec idle | 170, 100, 50, 0 ms | Keep 40 + 90 ms; compare protocol success and actual silent gap |
| Common recent-stop floor | existing 50 ms, then 25/0 experimentally | Separate from pre-codec settle; never accidentally count both twice |
| Post-STATUS wait | existing 40 ms, then 20/0 experimentally | Hold chosen pre-codec and 90 ms constant |
| Pre-clear-halt wait | existing 90 ms, then 60/40/20/0 experimentally | Hold all other validated timings constant |

Main's 50 ms is a minimum time since stop, not an additional unconditional wait.
Diagnostic mode 4 waits 170 + 40 + 90 ms plus USB/scheduling overhead; it does
not add a separate 50 ms. Decide explicitly whether a shared helper uses
`max(live_settle_ms, recent-stop minimum)`; if so, a zero setting is not a true
zero-idle test. Instrument actual stop-to-codec time and use a separately approved
diagnostic sweep to isolate/remove that floor. Do not change several waits at once.
The 200 ms rate-change settle is separate and out of scope for same-rate live apply.

For each candidate, test at least 20 ON/OFF cycles per control class and rate,
capture-only/playback-only/duplex, then a 100-toggle stress run of the selected
candidate. Record every USB result, first-real-data latency, audible route state,
timer jitter, inserted/discarded frames, XRUNs and watchdog activity. Reject a
shorter setting on any latch failure or recovery dependency. Recheck normal
cold starts/rate changes after factoring shared helpers; successful live apply
must not regress those paths. No sweep has been performed for this design.

## 9. Test and release plan

Before device tests: offline frame-accounting tests for ring wrap, fractional
44.1/88.2 kHz cadence, five and hundreds of gaps, partial periods, queued playback
credits, timer/URB races and stale generations. Exercise coalescing at every commit
stage, worker-exit queue races, stop/close with the peer still running, terminal
USB errors, failed submits, watchdog timeout, suspend and unplug. Review lock
ordering (including lockdep/KASAN runs when a suitable test kernel is available).
Build W=1 only after implementation is approved; none was done for this proposal.

Hardware matrix: all four rates, capture-only/playback-only/duplex, each codec
control in both directions, valid source selections on both pairs, rapid mixed
control bursts and Mono interlocks. Verify the actual routed audio, not just the
control getter. Use analog routing/markers, never S/PDIF loopback. Check Digital
Input Lock off and requested GET_CUR rate. Use `plughw` or correct SoX conversion
for playback; never reinterpret a 32-bit WAV as hardware S24_3LE.

REAPER acceptance at 128/256/512 frames and 2/3 periods:

1. Establish a no-toggle ten-minute baseline and log exact rate, period size,
   buffer size, wall-clock start/stop markers and captured frame count.
2. Record ten minutes with playback active and five separated panel toggles
   (e.g. at 60/150/240/330/420 s); include Direct, PCM/Mono and source changes
   across the full test suite. Repeat with capture alone and control bursts.
3. Independently timestamp actual acquisition start/end using CLOCK_MONOTONIC
   and sample-indexed markers; do not use shell launch duration, REAPER's own
   sample-derived counter alone, or `arecord -d 600` as proof of continuity.
   A fixed requested frame count is a tautological file-length test.
4. Check the raw recorded item/file's exact frames (no export padding, resampling
   or time stretching). With N frames and rate R, require
   `abs(N / R - measured_acquisition_seconds) < period_frames / R`.
   Measurement uncertainty and start/stop alignment must be below that budget.
5. Locate each inserted silent interval and compare its frame length with the
   measured missing-data interval/analog markers. Subsequent markers stay aligned;
   no concatenated waveform jump or repeated old playback segment. Log silence
   and discard frame totals independently of genuine USB throughput.
6. Require no EIO/XRUN, no stuck/backward pointer, no unexpected watchdog recovery,
   correct final hardware state and successful repeated stop/start/close. A normal
   two-second-buffer or normal-user-buffer PASS alone is insufficient.

An independent hardware sample clock can drift relative to CLOCK_MONOTONIC even
without toggles. At 48 kHz, a 128-frame tolerance over 600 s is about **4.44 ppm**.
Measure baseline drift separately; do not silently subtract it and declare the
user's absolute wall-clock criterion passed. If baseline already exceeds the
limit, a gap-only bridge cannot guarantee that criterion: agree an explicit
clock-discipline/resampling solution or revised criterion before release.

## 10. Decisions/open questions before implementation

- Approve the desired-state lock and generation protocol, including the explicit
  pre-resubmit coalescing fence. Late changes need another transaction; propose
  a finite control-flood budget rather than an unbounded silent interval.
- Approve separating playback reservation and elapsed cursors. A simple timer
  around the old hwptr updates is insufficient; normal playback accounting and
  delay reporting must be regression-tested as part of this change.
- Determine first-capture-batch latency/stale-data behavior and the baseline clock
  drift. These are measured unknowns, not solved by nominal-rate timer arithmetic.
- Select a finite whole-transaction/recovery timeout and user-visible asynchronous
  error indication. Proposal: preserve desired state for next start, log applied
  generation/error, and expose a read-only apply-status control; do not silently
  report success or keep synthetic silence indefinitely after genuine failure.
- Confirm conservative 170 ms until the sweep validates a shorter default, and
  whether to retain the 50 ms shared recent-stop floor for production live apply.
- Approve resetting both RIAA pairs after every full gap, beyond the mandatory
  affected-pair reset on source change.

## 11. Addendum (2026-10-16): phase 3a failure recovery (retry, fallback, XRUN)

Phase 3a (`design/v0.1.12`, `px_live_apply_work()`/`px_live_apply_restart()`)
implemented the simpler, already-proven `mutex_trylock()` +
`cancel_delayed_work_sync()` pattern from `px_cap_watchdog_fn()`, not section
5's two-phase teardown proposal above - a deliberate choice at implementation
time, not an oversight (the watchdog pattern was already hardware-validated;
the elaborate lifecycle-gate scheme above was never built or tested). An
offline model-check against the watchdog reference (trylock/cancel/
coalescing/deadline properties) found that divergence sound: event-triggered
scheduling instead of an unconditional self-reschedule is the right shape for
a debounce-and-apply worker, not a watchdog-style continuous poll, and the
trylock/cancel pairing relies on the same kernel guarantee (`cancel_work_sync()`
correctly terminates even a work item that requeues itself from within its
own execution) the watchdog already exercises on real hardware.

The model-check did surface one real gap: `px_live_apply_restart()`'s failure
path (`fail:`) calls `px_kill_audio_urbs()`, which kills playback, feedback,
and capture URBs together. If nothing else bumps `desired_gen` afterward, the
worker never retries itself, and the existing capture watchdog's own recovery
action - confirmed by reading it - only ever resubmits feedback and capture
URBs (interface 1), never playback (interface 0); that scope is correct for
the watchdog's original, narrower purpose and predates this feature. Net
effect without changes here: a failed live-apply restart could leave playback
silently dead until the user manually restarts their stream - a new exposure,
since nothing before `px_live_apply_restart()` ever killed and resubmitted
audio URBs mid-stream outside the existing start/stop boundaries.

**Decision: option B.** `px_live_apply_restart()` (and the retry/fallback
logic wrapped around it in `px_live_apply_work()`) owns its own complete
failure recovery. The capture watchdog stays capture-only and unchanged -
extending its scope to cover playback was the alternative (option A) and
was rejected in favor of keeping the two recovery mechanisms independent and
narrowly scoped to what each already understands.

### Design

1. **Retry.** On failure at any step, retry the full restart at most twice
   (3 attempts total) with backoff ~100 ms then ~300 ms, under the single
   `mutex_trylock()` acquired at worker entry (the whole retry sequence runs
   under one continuous `px->mutex` hold, not a re-acquired one per attempt -
   simplest, and avoids re-checking `running`/`disconnected`/the snapshot
   mid-sequence). Every failing attempt is logged with the step that failed
   and its return code.
2. **Fallback, without a codec apply.** If all retries fail and the device is
   still present: resubmit capture, feedback, and playback URBs in the normal
   start order (matching `px_start_streaming()`), skipping every codec/rate/
   status control transfer entirely - the device keeps whatever codec state
   was last genuinely applied. `desired_gen` is deliberately left different
   from `live_applied_gen` so a later control change, or the next stream
   start's `px_codec_resync_shadow()`, tries the real apply again. (A
   read-only "apply pending" indicator for the panel, foreshadowed by
   section 10's open question, is still not implemented here - `desired_gen
   != live_applied_gen` is already the data a future control would read.)
3. **Never fail silently.** If the fallback resubmit itself also fails for a
   reason other than the device being gone, force an XRUN
   (`snd_pcm_stop_xrun()`) on whichever substream(s) are open, so the DAW
   goes through `prepare()` -> `px_start_streaming()` - the one, proven,
   fully-tested recovery path - instead of silently sitting on dead URBs.
   ENODEV/ESHUTDOWN anywhere in this flow (an attempt, the fallback, or
   both) means the device is gone: stop immediately, no further retries, no
   XRUN call - `px_disconnect()` owns teardown from here, and calling PCM
   ops against a vanishing device adds risk without benefit.
4. **Fault injection.** `live_fail_step` (module param, `uint`, 0644, default
   0) deterministically fails one named step of `px_live_apply_restart()`:
   `1`=status read, `2`=codec write, `3`=SET_CUR rate, `4`=status write,
   `5`=URB resubmit. Step 5 is checked in *both* the main restart's resubmit
   loop and the fallback's resubmit loop, so a single value drives the
   "fallback also fails" -> XRUN scenario end to end, while 1-4 only affect
   the codec-touching main restart - the codec-free fallback is unaffected by
   them and succeeds, exercising the "retries exhausted, fallback restores
   playback" scenario instead. This asymmetry is deliberate, not an
   oversight: it lets one param reach either terminal outcome without a
   larger fault-injection surface. ENODEV/ESHUTDOWN itself is not
   fault-injectable (it's a real disconnect condition) - see the model below.

### Offline model: six scenarios

Reasoned against the actual implementation (`px_live_apply_work()`,
`px_live_apply_restart()`, `px_live_apply_fallback()`), not just the design
above - filled in after implementation, before any hardware test:

| Scenario | Path exercised | Outcome |
|---|---|---|
| fail-once (retry recovers) | `live_fail_step=N` (1-4), manually cleared during the ~100 ms backoff before attempt 2 | Attempt 1 fails and logs step+rc; attempt 2 (fault cleared) succeeds; `live_applied_gen` updates; no fallback, no XRUN |
| fail-always-control (fallback restores playback) | `live_fail_step=1..4` left set | All 3 attempts fail (logged each time); fallback skips codec/rate/status entirely, so it's unaffected and succeeds; stream resumes on the *old* codec state; `desired_gen != live_applied_gen` persists |
| fail-submit (XRUN) | `live_fail_step=5` left set | All 3 attempts fail at URB resubmit; fallback's own resubmit loop also checks step 5 and fails too; `px_live_apply_xrun()` stops the open substream(s); DAW re-prepares through the proven start path |
| ENODEV (stops cleanly) | real disconnect during an attempt or the fallback (not fault-injectable) | `px_is_device_gone()` true on first sighting; no further retries, no fallback, no XRUN call; `requeue` is forced false; `px_disconnect()`'s own `cancel_delayed_work_sync()` (belt-and-braces call already present) owns teardown |
| toggle during a retry (coalescing) | a control changes while attempts 1-3 and/or the fallback are in flight (test procedure, not new code) | `px_switch_put()`/`px_adc_source_put()` bump `desired_gen` and call `schedule_delayed_work(0)` regardless of what the worker is doing; the worker's own `requeue = px->desired_gen != gen` check at the end (now gated `!device_gone &&`) re-arms once for the latest snapshot - not per intermediate edit, and not at all if the device turned out to be gone |
| stop/close during a retry | `px_pcm_close()`/`px_stop_streaming()` called while the worker holds `px->mutex` across a retry+backoff+fallback sequence | `close()`'s `mutex_lock(&px->mutex)` blocks until the worker's current (bounded, at most a few hundred ms to ~1-2 s worst case across 3 attempts + fallback) sequence finishes and releases the mutex - not a deadlock, a bounded wait, the same trade-off `px_start_streaming()` already makes by holding the mutex across its own settle sleeps. Once acquired, `cancel_delayed_work_sync()` in `px_stop_streaming()` is cancelling an instance that has either not started or has already fully finished - never one actively holding the mutex - so it cannot itself hang |

Not reachable via `live_fail_step`: a genuine mid-retry disconnect (ENODEV
row above) needs an actual unplug during a hardware test, not a fault-
injection run.

Unlike sections 1-10 below (proposal only when written), this addendum *is*

scoped it - still build-only, no hardware test, pending a separate go-ahead

## 12. Addendum (2026-10-17): hardware hang during the first live-apply test, and the fix

First hardware test of phase 3a (`0.1.12-pre1`, scenario (a) of
`tests/hw/v0112-live-apply-checklist.md`) hung the kernel - hard power-off
required. Code analysis and fix below; no hardware access performed for
either. What happened (user's own report, condensed): REAPER on ALSA
`hw:PhaseX64`, 48kHz, recording In 1/2, PipeWire off. Two clicks in the
*installed* 0.1.11.5 panel (`In 1/2 Capture Source`: Phono -> Aux -> Phono)
- Aux correctly went silent, confirming the live apply worked - then the
stream died (no play/record), REAPER could not quit or save.
`test_live_apply.py gaps` showed **8 generations for 2 clicks**, each
~310ms apart. `/proc/asound/.../pcm0c/sub0/status` and `.../pcm0p/sub0/
status` both showed `XRUN`, capture's `hw_ptr` exactly one buffer ahead of
`appl_ptr`. dmesg showed capture URBs completing forever
(`active=0 running=1`). `ps -L` showed REAPER's audio thread in `D` state;
its kernel stack (`reaper-hang-stack.txt`) showed the real wait point:

```
px_pcm_sync_stop+0xac/0xf0 [snd_usb_phasex64]
snd_pcm_do_prepare+0x1c/0x50 [snd_pcm]
```

The rest of that file (re-checked, unchanged on a second look) is several
of REAPER's *other* threads, each independently caught in the coredump's
group-exit signal path (`get_signal`/`do_exit`/`do_group_exit`, repeated
once per thread) - consistent with the "main thread D in vfs_coredump...
waits for the audio thread" already reported. Worth stating plainly: the
original `wait_event()` is uninterruptible, not `wait_event_interruptible()`
or `_killable()` - even REAPER's own fatal coredump signal could not wake
the stuck thread, which is why the whole process hung rather than crashing
and dying cleanly.

**Correction**: an earlier revision of this note claimed
`wait_event_killable()` "would not have helped" - that was wrong, caught
on review. `TASK_KILLABLE` (what `_killable()` waits use) *is* woken by a
fatal signal, including the `SIGKILL`-class group-exit every thread of a
coredumping process receives - that is the entire distinction between it
and plain `wait_event()`'s `TASK_UNINTERRUPTIBLE`, which ignores every
signal including that one. The fix (below) now uses
`wait_event_killable_timeout()`, not `wait_event_timeout()`: bounded
*and* wakeable by a fatal signal, landing in the same forced-URB-teardown
recovery either way.

### Root cause 1: why `px_pcm_sync_stop()` hung forever

The stack trace is the key fact this analysis almost missed by assuming
the stuck caller was a close/stop path: `sync_stop` was called from
**`prepare`**, not from `close`/`hw_free`. This is correct, documented
ALSA behavior, not a bug on its own - `sync_stop` exists precisely because
the core calls it at `prepare`/`hw_free`/`hw_params`, the points where it
must wait for an in-flight stop to finish (upstream rationale: stopping a
stream is atomic/interrupt-context-safe, so a period-elapsed call can
still be in flight when `trigger(STOP)` returns, and the wait for it to
finish has to happen somewhere that can sleep - `sync_stop` is that
somewhere). REAPER's XRUN-recovery path (standard ALSA practice: call
`snd_pcm_prepare()` to recover from `XRUN`) reached `sync_stop` completely
normally.

The actual gap: **`px_stop_streaming()` - the only place that cancelled
`live_apply_work` - is called from `hw_free()`/`close()`, both of which
come *after* `sync_stop()` in the normal teardown order.** At the moment
`sync_stop()` was stuck, `px_stop_streaming()` had not run yet and
couldn't: the thread was blocked earlier in the sequence. So whatever
mechanism caused `in_elapsed` to never reach zero, the one thing that
would have resynchronized everything (cancelling live-apply, killing
URBs, clearing `px->running`) was never reached - a bounded wait with a
forced-recovery fallback, requested in the original task list, is
necessary regardless of pinning the exact lost-decrement mechanism, and a
closer code read found the better fix sits one level up: move the
synchronization into `sync_stop` itself, the earliest point in the
sequence that both runs in process context (can sleep/cancel) and is
guaranteed to run before anything else proceeds.

Full code read of `px_cap_complete()`/`px_play_complete()`'s `in_elapsed`
increment/decrement pairing did not find a structural bug - both are
gated on `s->active` (confirmed false in the later dmesg), and the
increment and matching decrement happen within the same completion
callback with no early-return between them. The exact mechanism that left
`in_elapsed` non-zero is not nailed down with certainty from static
analysis alone (a plausible candidate: a completion racing the exact
instant `trigger(STOP)` flips `active`, landing in a narrow window this
analysis could not rule out without kernel-side tracing) - but removing
the *trigger* for the race (a live-apply restart resubmitting URBs
concurrently with the stop/prepare sequence) removes the need to pin the
mechanism exactly, since the fix no longer depends on it.

### Root cause 2: the XRUN itself

Best-supported explanation, from the evidence available (not from a
missing trace that would have confirmed it directly - see "what's still
open" below): **the coalescing failure (8 restarts instead of 1-2, see
below) compounded phase 3a's own explicitly-accepted tradeoff "no
completions during the kill-to-resubmit gap" eight times in rapid
succession** (section 1: "~0.3s is missing at each toggle"). A single
~300ms gap is the known, accepted cost of one live apply; eight of them,
~310ms apart, in under 2.5 seconds, is sustained enough silence that
either REAPER's own buffer-starvation detection or the core's position-
consistency check would plausibly declare XRUN on its own - this does not
require `px_live_apply_xrun()` (the fallback-of-last-resort added in
section 11) to have fired for a genuine failure; ordinary ALSA XRUN
detection reacting to compounded, repeated gaps is sufficient and matches
the evidence without assuming a hardware fault occurred.

### Root cause 3: why 8 generations for 2 clicks

Not resolved with certainty - flagged here rather than guessed at.
Checked and ruled out: every click path in the panel (`build_skin`'s
`click()` and `build_plain`'s radio buttons, both the skinned and plain
UI) calls `self.write([(name, value)])` with exactly one control per
click, in both the installed 0.1.11.5 panel and this branch's panel -
there is no bulk-write path that could turn 2 clicks into more than 2
writes. Every `schedule_delayed_work(&px->live_apply_work, ...)` call
site in the driver was checked (`px_switch_put()`, `px_adc_source_put()`,
the trylock-retry path, and the end-of-worker coalescing requeue) - none
bumps `desired_gen` more than once per accepted (changed-value) write, and
`px_codec_write()`'s own `desired_codec` mirroring (used during a live
apply's register replay) deliberately does not touch `desired_gen` or
reschedule anything (checked specifically to rule out a feedback loop).
If the panel and the driver both only ever act on genuine, distinct
writes, 8 generations implies 8 distinct accepted writes reached the
driver, not a driver-side generation-count bug - but this analysis cannot
confirm that from the data available. **What's missing**: the raw
`staged gen=N (...)` dmesg lines, which name the triggering control per
generation (added in the previous session specifically for this kind of
diagnosis) - not captured for this incident. The safer next test (below)
asks for exactly this data.

### The fix

1. **`px_pcm_sync_stop()` now cancels `live_apply_work` synchronously,
   first, before waiting on `in_elapsed`.** `sync_stop` is one of the
   exact synchronization points the kernel's own contract gives drivers
   for "make sure nothing else is touching this stream" - a live-apply
   restart concurrently killing/resubmitting URBs is exactly the kind of
   in-flight activity that contract exists to drain, and doing it here
   (rather than only in `px_stop_streaming()`) reaches the synchronization
   point `prepare` actually needs, not just `close`. Safe against
   `px->mutex`: `px_live_apply_work()` only ever `mutex_trylock()`s it, so
   this can never block on a worker itself waiting on something
   `sync_stop`'s caller holds - the same invariant `px_stop_streaming()`'s
   existing (now redundant-in-the-common-case, still correct as
   belt-and-braces) cancellation already relied on.
2. **`wait_event()` is now `wait_event_killable_timeout()`, bounded at
   1000ms and wakeable by a fatal signal.** Independent of (1) actually
   eliminating every way `in_elapsed` could get stuck - "never block
   indefinitely" per the task, not per how confident this fix is in
   having found the one true cause - and independent of the calling
   process being able to exit cleanly on its own, which this incident
   showed cannot be assumed (see the stack-trace correction above). On
   timeout *or* a fatal signal: force-kill every audio URB (capture+
   feedback+playback, not just this substream's - they retrigger
   together), reset `in_elapsed` to 0 (the only honest value once no URBs
   are outstanding), warn so this is never silent.
3. **`px_live_apply_restart()`/`px_live_apply_fallback()` now re-check
   `px->running` immediately before their resubmit loops**, not only at
   `px_live_apply_work()`'s entry - both functions run long enough
   (settle sleeps, several retried control transfers) that a stop could
   have been requested since that early check. `px->mutex` is held
   throughout by the caller's contract (same as `px->running` itself only
   ever being written under it), so this read needed no new lock. On a
   stop detected this way, both functions return `-ESHUTDOWN`, which
   `px_is_device_gone()` already treats the same as a real disconnect in
   the caller: no fallback attempted, no XRUN forced - the stream is
   already being torn down through its own proper path.
4. **All three `schedule_delayed_work(&px->live_apply_work, 0)` call
   sites now use a fixed `LIVE_APPLY_DEBOUNCE_MS` (30ms) instead of 0.**
   Addresses root cause 3 structurally, not by having found and fixed a
   specific bug that produced exactly 8 (none was found - see "root cause
   3" above). `schedule_delayed_work()`'s own "already pending" coalescing
   only protects a burst landing while a previous schedule is still
   *queued*; at delay=0 that window is however long it takes the
   workqueue to dequeue and start running the work - often under 1ms, far
   shorter than realistic back-to-back user actions (or whatever produced
   8 commits for 2 clicks here). 30ms costs nothing user-visible against
   this feature's own "fast enough to not notice" goal, and widens the
   coalescing window to something that actually covers normal rapid
   interaction. Applied at all three sites that schedule with delay=0
   (both `put()` functions and the end-of-worker mid-restart requeue) for
   consistency, not just the two directly tied to user clicks.

Together: (1)+(2) make `sync_stop` itself bounded, self-healing, and
unblockable-by-a-dying-caller regardless of root cause; (3) makes the
worker stop trying to resubmit onto a stream that's going away, the
moment it can tell; (4) reduces the opportunity for root cause 3's
pattern to recur, without claiming to have fixed its exact cause. Build:
`W=1`, zero warnings (`checkpatch.pl`: 0 errors, same 36 warnings as the
previous revision of this fix, no new category). No module load/unload,
no device access.

### Why it can't hang the same way again

Walking the exact failure sequence through the fix: trigger(STOP)/XRUN
sets `active=false` -> REAPER calls `prepare()` -> core calls
`sync_stop()` -> **first thing, `cancel_delayed_work_sync(&px->
live_apply_work)` runs and waits for any in-flight restart to fully
finish (bounded by that restart's own worst case, ~1-2s, not infinite -
see "what's still open" below) and prevents any *new* one from starting**
-> only then does the `in_elapsed` wait begin, now with nothing left that
could still be resubmitting URBs for this device -> even if `in_elapsed`
somehow still doesn't reach 0 within 1000ms, *or* the calling process
receives a fatal signal before then (this incident's actual case - the
coredump's own group-exit, which the original `wait_event()` could not
observe at all), the same forced-URB-teardown path runs and the function
returns, not hangs. Any live-apply attempt that *was* cancelled mid-flight,
or one that checks `px->running` right before its own resubmit and finds
it false, exits via `-ESHUTDOWN` instead of touching URBs at all.

### Offline model: two new scenarios

Added to the six from section 11, reasoned against the fixed code:

| scenario | path exercised | outcome |
|---|---|---|
| stop/close while a restart is in flight | `px_pcm_sync_stop()` called while `px_live_apply_work()` holds `px->mutex` mid-restart | `cancel_delayed_work_sync()` blocks until that restart finishes (bounded by its own retry/backoff ceiling) *or* the restart's own pre-resubmit `px->running` check fires first if the stop became visible in time; either way `sync_stop` proceeds once it returns, never racing a resubmit |
| XRUN while a restart is in flight (this incident) | the stream enters XRUN (core-detected or `px_live_apply_xrun()`) while `px_live_apply_work()` is mid-sequence | `trigger(STOP)` (called as part of the XRUN transition) sets `active=false` immediately, atomic context, no wait; the in-flight restart either finishes and the *next* `prepare`'s `sync_stop` cancels/drains it, or a later resubmit inside that same restart hits the new `px->running` re-check - `px->running` itself doesn't go false here (XRUN isn't a close), so this path relies on (1) and (3) together, not on `px->running` alone |

**What's still open, not a unit/offline-model test**: a true automated
test of this specific interaction (ALSA core's `sync_stop`/`prepare`
sequencing, real `wait_event_timeout`, real workqueue cancellation
semantics) isn't practically mockable at the userspace level the way
`midi_in_filter.c`'s pure parsing logic is - this section's written
walk-through is the offline model, matching how section 11's six
scenarios were verified, not a gap deferred without reason.
`cancel_delayed_work_sync()` in `sync_stop` is itself unbounded in the
abstract, bounded in practice only by the live-apply worker's own
worst-case runtime - the old "~1-2s worst case" estimate here was wrong
(only counted the settle sleep and backoff, not the control-transfer
retry timeouts); see "Review round 2" below for the corrected number
(~92s pathological worst case, not 1-2s) and why this is still a finite,
acceptable bound rather than a residual risk to fix further right now.

### Review round 2 (2026-10-17): lock-ordering proof, worst-case runtime, diagnostics, in_elapsed audit

A second review round, before any further hardware testing, asked for
five things: a precise lock-ordering proof (not just "believed safe"), a
computed worst-case worker runtime, diagnostic logging, a focused
re-audit of every `in_elapsed` mutation, and corrections to the test
plan's own claims. All code changes below are in commit history on
`design/v0.1.12` (not pushed); this section documents the reasoning.

**1. Lock-ordering proof.** The previous revision's safety argument
("`px_live_apply_work()` only ever `mutex_trylock()`s `px->mutex`, so it
can't block `cancel_delayed_work_sync()`'s caller") was correct but
incomplete: it covered `px->mutex`, not the ALSA PCM core's own internal
locking, which is what the hang actually went through (the stack trace
shows `sync_stop` called from `snd_pcm_do_prepare`, itself called via
`snd_pcm_action_single`/`snd_pcm_action_nonatomic` - upstream's nonatomic
action path holds a lock across that entire call chain, per the
mechanism `sync_stop` was added for in 2019 - Takashi Iwai's original
commit message: "this gets called at the appropriate places that need a
sync with the stream-stop, i.e. at hw_params, prepare and hw_free").
`hw_params`/`hw_free` reach `sync_stop` too, but through the newer
(2022) `runtime->buffer_mutex` added specifically to fix "races among
concurrent hw_params and hw_free calls" - a different lock from
`prepare`'s action-group lock, not the same one. This driver cannot
state with certainty which exact core lock is held at every call site
without reading the exact installed kernel's `sound/core/pcm_native.c`
(not available in this environment - only kernel headers are installed,
not core subsystem source), and does not need to: **the live-apply
worker's own fix is to never acquire any ALSA-core lock at all**, which
makes the proof independent of exactly which core lock each caller
holds. Concretely, `px_live_apply_work()` (and everything it calls -
`px_live_apply_restart()`, `px_live_apply_fallback()`,
`px_live_apply_give_up()`) now only ever touches: `px->mutex`
(`mutex_trylock()`, never blocks - see that function's own comment),
`desired_lock` (a plain spinlock, held only briefly, never nested inside
`px->mutex` or any stream lock), and USB-core calls (`usb_kill_urb`,
`usb_submit_urb`, `usb_control_msg_send`/`recv`, `usb_clear_halt`) whose
own locking is entirely internal to the USB subsystem, not shared with
ALSA PCM core locks. The one call that *did* reach into the PCM core -
`snd_pcm_stop_xrun()`, inside the now-removed `px_live_apply_xrun()` -
has been deleted, replaced with a log-only `px_live_apply_give_up()`
(see that function's own comment for the full removal rationale). With
that gone, `cancel_delayed_work_sync()` waiting on this worker from
inside *any* ALSA-core lock, whichever one it turns out to be, cannot
deadlock against it - the worker never asks for that lock, or any lock
in that subsystem, at all. This is weaker than naming the exact lock and
showing it's never acquired reflexively, but stronger than "believed
safe": it holds regardless of which lock each `sync_stop` caller turns
out to use.

**2. Worst-case worker runtime.** Every USB control transfer in the
live-apply path goes through `px_ctrl_retry()` (status read/write, codec
writes, `SET_CUR` rate x2 pairs) or is a single bounded call
(`px_get_rate_ep()`'s rate-verify read, `usb_clear_halt()`). All are
finite: `px_ctrl_retry()` caps at `CTRL_ETIMEDOUT_RETRIES` (1) extra
attempt on `-ETIMEDOUT`, each attempt bounded by `CTRL_TIMEOUT` (1000ms),
so a single call's worst case is 2 x 1000ms + `CTRL_RETRY_DELAY_MS`
(20ms) = **2020ms** (the `-EPIPE` path is bounded separately at 3
retries x 20ms and fails fast, well under this). `usb_clear_halt()` is
usbcore's own function, bounded by its own fixed `USB_CTRL_SET_TIMEOUT`
(5000ms upstream, not configurable by this driver). Summing one full
`px_live_apply_restart()` attempt's worst case: settle sleep (capped at
500ms by `min_t()` regardless of the `live_settle_ms` module param) +
status read (2020ms) + up to 6 codec register writes (6 x 2020ms =
12120ms, per that loop's own "six logical writes at most" design
invariant - R7/R21/R22 x 2 codecs, the only registers this driver's own
logic ever stages) + 2x `SET_CUR` capture rate + 1x play rate (3 x
2020ms = 6060ms) + rate-verify read (1000ms) + status write (2020ms) +
two fixed sleeps (40ms + `CLEAR_HALT_DELAY_MS` 90ms) + `usb_clear_halt`
(5000ms) = **28850ms** per attempt. `px_live_apply_work()` runs this up
to `LIVE_APPLY_MAX_RETRIES + 1` (3) times with fixed backoff (100ms +
300ms between attempts, per `live_apply_backoff_ms[]`), then
`px_live_apply_fallback()` once (its own worst case: `CLEAR_HALT_DELAY_MS`
+ `usb_clear_halt` = 5090ms; no control transfers). **Total worst-case
`px_live_apply_work()` runtime: 3 x 28850 + 400 + 5090 = 92040ms, ~92
seconds** - all while holding `px->mutex`. This replaces "residual risk,
not fixed" with an actual number, and the number is much larger than the
"~1-2s" this document previously assumed (that estimate only counted the
settle sleep and backoff, not the control-transfer retry timeouts - an
oversight, not a deliberate simplification). **Important caveat**: this
92s figure is the pathological case where every single control transfer
genuinely times out (`-ETIMEDOUT`) rather than failing fast
(`-EPIPE`) or succeeding - e.g. a wedged device mid-sequence. It is
*not* exercised by `live_fail_step` fault injection (scenarios c/d in the
checklist), which short-circuits before any real USB wait, so those
tests validate the retry/fallback *logic*, not this worst-case *timing*.
The practical consequence: `px_pcm_sync_stop()`'s own total worst-case
latency (via `cancel_delayed_work_sync()`, which blocks for however long
a concurrently-running worker instance takes, plus its own
`SYNC_STOP_TIMEOUT_MS` wait after that) is this ~92s plus ~1s, **not**
the sub-2-second figure the checklist's scenario (d) previously claimed -
corrected there (see below). Still finite - the core guarantee - just
slower in the pathological case than previously stated. Not changed
further in this round: tightening the live-apply path's own timeouts
(e.g. a shorter `CTRL_TIMEOUT` specific to this path) is a reasonable
follow-up but out of scope for a review response: flagging it as an
option, not implementing it unasked.

**3. Diagnostics.** Added `px_sync_stop_diag()`, a shared snapshot
helper called at `sync_stop` entry (`dev_dbg`) and again on the
timeout/kill path (`dev_warn_ratelimited`, not plain `dev_warn` - this
path firing even once is noteworthy but must never itself flood the
log): reports both streams' `in_elapsed` and `active`, `running`,
`urbs_live`, `desired_gen`, `live_applied_gen`, and the capture-only
`cap_complete_count`/`last_cap_urb_status`/`last_cap_urb_actual_length`
(there is no symmetric playback-side equivalent of the last two fields -
the watchdog only ever needed them for capture, not added here for
playback since nothing currently reads them). The "staged gen=N" traces
in `px_switch_put()`/`px_adc_source_put()` now also log the kcontrol's
`numid` and the calling process's `comm`/`pid` (via `current`, valid
since `put()` runs in the calling process's own context from the ioctl
syscall) - together these let a future test session see, per generation,
which control and which process (panel, `amixer`, a DAW's own mixer)
triggered it, resolving root cause 3's open question directly from
dmesg instead of by elimination.

**4. `in_elapsed` audit.** Re-read every mutation site
(`px_play_complete()`/`px_cap_complete()`'s inc/dec pairs,
`px_pcm_sync_stop()`'s forced reset, the two `atomic_set(..., 0)` init
sites) specifically against the live-apply kill/resubmit/fallback paths.
Finding: **no bug found, and the reasoning now has a basis stronger than
"didn't find one"**. `px_kill_audio_urbs()` (called at the top of
`px_live_apply_restart()`, and by `px_stop_streaming()`) calls
`usb_kill_urb()` on every capture/feedback/playback URB. `usb_kill_urb()`
is synchronous per URB - it does not return until that URB has no
completion callback in flight, *including* one that resubmits itself
(the exact pattern `px_cap_complete()`/`px_play_complete()` use,
resubmitting before the `in_elapsed` increment/decrement pair that
brackets the `snd_pcm_period_elapsed()` call) - this is the API's
documented purpose and the reason USB drivers can resubmit from inside
their own completion handler safely under a concurrent kill. Consequence:
by the time `px_kill_audio_urbs()` returns, every URB is idle and
`in_elapsed` is back at 0 for both streams, *before* any control
transfer in the restart sequence runs - and since no URB is submitted
again until the resubmit step at the very end, nothing can increment
`in_elapsed` during the whole settle/codec-write/rate/status-write
window, so there is no window in which a restart "kills URBs while a
completion counted in_elapsed" the way the review asked to check for.
The only way `in_elapsed` is non-zero when `sync_stop`'s own wait begins
is the ordinary case - a genuinely in-flight completion on an actively
running stream, which resolves in the time it takes to copy a buffer and
call `snd_pcm_period_elapsed()` (microseconds), not anywhere near the
1000ms timeout. This confirms, rather than just asserts, that the fix
does not depend on hitting that timeout in the normal case.

**5. Test plan corrections** - see `tests/hw/v0112-live-apply-checklist.md`
(status note and scenario (d) both updated) and the "Proposed safer next
hardware test" list below: the `timeout`/`-d`-bounded-process framing
was wrong in the same way for both - neither an external `timeout`
wrapper nor `arecord -d N`'s own internal counter can rescue a process
stuck in a `TASK_UNINTERRUPTIBLE` (D-state) kernel wait, since both
require the process to return to userspace to notice elapsed time or a
non-fatal signal; only the driver's *own* bounded/killable wait (this

### Review round 3 (2026-10-17): reconciling the hang, bounding cancel, and a real give-up path

A third review round, still before any hardware test, asked three things:
reconcile the hang against the *exact* pre-fix wait condition (not the
current, already-patched one), bound `cancel_delayed_work_sync()`'s
latency instead of accepting ~92s, and replace the give-up path's
logging-only behavior with something that actually marks the stream
failed. All three are addressed below and in commit history (not
pushed).

**1. Reconciling the hang.** The exact code that hung (`418de8e`, before
`a92f430`) was:

```c
static int px_pcm_sync_stop(struct snd_pcm_substream *sub)
{
	struct px_dev *px = snd_pcm_substream_chip(sub);
	struct px_stream *s = px_stream_of(px, sub);

	wait_event(s->elapsed_wq, atomic_read(&s->in_elapsed) == 0);
	return 0;
}
```

No `cancel_delayed_work_sync()`, no lock, nothing else - just this one
wait. The suggested hypothesis ("did it wait on URBs in flight, which
never drops while running=1 keeps resubmitting?") does **not** hold up
against the completion handlers' own code, and it's worth showing why
precisely rather than just asserting it: `px_cap_complete()`/
`px_play_complete()` only increment `in_elapsed` inside a block gated on
`s->active` (`if (s->active && urb->status == 0 && ...)` -
`phasex64.c`, the block right after `spin_lock_irqsave(&s->lock, ...)`),
and `px_pcm_trigger()`'s `STOP` case clears `s->active` under that exact
same lock (`spin_lock_irqsave(&s->lock, flags); s->active = false; ...`).
Resubmission (`usb_submit_urb()`) *does* happen unconditionally whenever
`px->running` - that part of the hypothesis is correct, and it is a real,
confirmed behavior (matches "capture URBs completing forever with
active=0 running=1" exactly) - but it is also **deliberate, existing
design**, not a bug: URBs are meant to keep flowing continuously across
ordinary stop/restart cycles (pause/resume, XRUN auto-recovery) so those
cycles don't pay a kill+resubmit cost every time, the same cost phase 3a
already treats as expensive enough to coalesce around (section 3). Once
`active` is false, though, the *increment* path is closed - a completion
arriving with `active=false` computes nothing and does not touch
`in_elapsed` at all. So resubmission-without-stopping explains the
observed URB/trigger state, but does not, by itself, explain why
`in_elapsed` could still be the thing `sync_stop` was stuck waiting on -
changing the resubmission gating to fix that would also give up the
pause/resume design deliberately kept cheap, for a problem it doesn't
actually explain.

Given `in_elapsed`'s own bookkeeping is internally consistent (every
increment pairs with a decrement inside the same completion callback,
both outside any lock this driver controls), the only way it stays
*stuck* non-zero, rather than merely transiently non-zero for a
microsecond, is if one specific call to `snd_pcm_period_elapsed()` -
made by the one completion that raced the exact instant `active` flipped
- itself did not return. This driver does not own that function; it
cannot be patched from here, and this review cannot prove from static
reading alone which lock it needed or who else held it. What *is*
concretely confirmed by diffing the hung build against the fix: **the
pre-fix build had zero coordination between the live-apply worker and
`sync_stop`/`prepare` - the worker's own `px_live_apply_restart()` (same
commit range) had no `px->running` re-check before resubmitting either**.
Two independently-operating URB lifecycle managers - REAPER's own
thread, stuck in `prepare()`'s `sync_stop`, and the live-apply worker,
mid-restart on a completely separate workqueue thread, during the
8-generations-in-2.5-seconds storm - had no way to even know about each
other. The most likely specific shape (not provable without kernel
tracing, which this review does not have access to and the user has
explicitly excluded hardware access for): `sync_stop` is reached from
inside the PCM core's nonatomic-action path, which (review round 2, item
1) holds a lock across the whole `prepare` action; if `snd_pcm_period_
elapsed()` also needs that same lock on certain paths (plausible - it
can itself trigger XRUN/notify handling), then a thread sitting inside
`sync_stop`'s `wait_event()` while *holding* that lock, waiting on a
condition that can only become true once some other completion's call
into that exact function returns, is a self-deadlock this driver's own
code cannot break out of - matching every observed symptom (stuck
exactly at that line, forever, regardless of how long it's given) without
requiring resubmission to be the mechanism.

This reasoning is why the committed fix does not try to "fix" the
in-flight completion claim further, and should not be read as "found and
fixed" so much as "found the fix doesn't need to know": whatever the
exact lock/thread involved turns out to be, `sync_stop` no longer can
wait on it unboundedly (bounded+killable wait, review round 1) and now
aborts in bounded time regardless of why the wait never resolves (review
round 3, item 2 below) - the safety property holds without pinning this
exact mechanism, which is the right scope for a fix this driver can
actually make, since the suspected deadlock partner (the PCM core's own
locking) is not this driver's code to change.

**2. Bounding cancel latency.** Added `px->live_apply_stopping` (a
refcount, not a bool - overlapping `sync_stop`/`stop_streaming` calls on
substreams that aren't explicitly linked must not have one clear it
while another still relies on it). `px_pcm_sync_stop()` and
`px_stop_streaming()` each `atomic_inc()` it immediately before their
`cancel_delayed_work_sync(&px->live_apply_work)` call and `atomic_dec()`
immediately after. `px_live_apply_restart()`/`px_live_apply_fallback()`
now check it via `px_live_apply_check_stopping()` before every sleep,
every control transfer, and (via the new `px_ctrl_retry_stoppable()`
macro, used in place of `px_ctrl_retry()` for every call in the live-apply
path) before every *retry* of a control transfer, aborting with
`-ESHUTDOWN` the instant it's set. **New worst-case cancel latency**:
bounded by whichever single operation was already in flight when the
flag was set, not the full sequence - the longest single such operation
is `usb_clear_halt()` (usbcore's own fixed timeout, ~5000ms, not
configurable here; checked for immediately before calling it, so this is
only paid if the flag became visible *after* that specific call already
started) or a single `px_ctrl_retry_stoppable()` attempt already past its
own first (uncancellable) try (at most `CTRL_TIMEOUT` = 1000ms, since the
check happens before deciding to retry, not mid-transfer). **Worst case:
~5000ms** (the `usb_clear_halt()` window), down from ~92000ms - a
genuine, large reduction, not a rounding adjustment. Not reduced further
in this round: shortening `usb_clear_halt()`'s own timeout would mean
reaching into usbcore's `USB_CTRL_SET_TIMEOUT`, not something this driver
can override per-call; flagged as a possible future follow-up (a
driver-local `usb_control_msg()`-based `CLEAR_FEATURE` call with a
shorter timeout, replacing `usb_clear_halt()` in this one path), not
implemented here since it wasn't asked for and changes USB-core-facing
behavior this review hasn't scoped. Also added: if the abort drops a
still-unapplied generation (`desired_gen != live_applied_gen` after the
cancel returns, nothing else would otherwise retry it), `px_pcm_sync_stop()`
reschedules the worker once, timed to land after the core's own
synchronous `prepare`/`hw_free` call that follows `sync_stop` - closes a
"silently drops the user's last control change" gap this abort mechanism
would otherwise introduce.

**3. A real give-up path.** `px_live_apply_give_up()` now sets a new
`px->give_up` flag (instead of only logging). `px_pcm_pointer()` returns
`SNDRV_PCM_POS_XRUN` while it's set - the documented, ALSA-core-sanctioned
sentinel a `.pointer` op uses to report XRUN; the core's own
`snd_pcm_update_hw_ptr0()` (reached on its own schedule, from wherever it
next polls position) does the actual XRUN handling, under its own
locking, with no call from this driver into the PCM core at all - keeping
exactly the lock-ordering property review round 2 removed
`px_live_apply_xrun()` to get. No URBs are resubmitted after give-up:
both failure paths that lead to it (`px_live_apply_restart()`'s and
`px_live_apply_fallback()`'s own `fail:` labels) already kill every URB
before returning, and `px_cap_watchdog_fn()` - the one other place that
can independently resubmit capture/feedback URBs on a stall - now checks
`give_up` too, so its own recovery can't race this state. Cleared only by
`px_start_streaming()`'s next successful run (also cleared defensively in
`px_stop_streaming()`, though that path doesn't need recovery since there
is no stream left to describe) - "the next prepare/start" is the one way
out, per the review's own framing.

### Review round 4 (2026-10-17): the self-deadlock hypothesis doesn't survive, reschedule replaced with a resync fix

A fourth review round pushed back on review round 3 item 1's
self-deadlock hypothesis with a concrete counter-argument, and asked for
a structural fix to replace round 3 item 2's reschedule. Still no
hardware access.

**1. The self-deadlock hypothesis is retracted.** The counter-argument:
if a completion were genuinely stuck inside `snd_pcm_period_elapsed()`
waiting on a lock another thread holds, either that lock is a spinlock
(in which case a CPU spinning on it from interrupt/softirq context for
this long would trigger a soft- or hard-lockup warning - none was
reported) or a sleeping lock (in which case a completion handler, which
generally cannot sleep - USB completions run from interrupt/tasklet
context - calling into something that tries to sleep on it would produce
an immediate "scheduling while atomic" / sleeping-in-invalid-context
splat, not a silent multi-minute hang - also not reported). Either way,
the hypothesis predicts a symptom that didn't show up. This is a better
argument than anything this review found on its own, and the hypothesis
is retracted rather than defended.

The suggested alternative - a lost wakeup, where `wait_event()`'s
caller misses a `wake_up()` because the waker changed the condition and
only *some* paths call `wake_up()` after - was checked exhaustively
against every version of this mechanism, not just since `d87e7aa`:
`in_elapsed`/`elapsed_wq` was introduced once, in `9490eff` ("fix NULL
deref panic in URB completion"), and has not been restructured since
except for `sync_stop`'s own wait (reviews 1-3, all on the *waiting*
side, not the increment/decrement side).

   a. **Every write to `in_elapsed`** (current file, same since `9490eff`
      for the completion-handler sites): `px_play_complete()` -
      `atomic_inc()` at line 739, paired `atomic_dec_and_test()` +
      `wake_up(&px->play.elapsed_wq)` at lines 760-761, both inside the
      same function call, using a single stack-local `elapsed` variable
      computed once under `s->lock` to decide both the increment
      (`if (elapsed) atomic_inc(...)`, inside the lock) and the matching
      decrement+wake (`if (elapsed) { ...; atomic_dec_and_test(...); }`,
      after it) - the same local variable, read twice in the same
      invocation, can't desync between the two reads. `px_cap_complete()`
      - identical shape, `atomic_inc()` at line 1035, paired
      `atomic_dec_and_test()` + `wake_up(&s->elapsed_wq)` at lines
      1063-1064. The two `atomic_set(..., 0)` calls in `px_probe()`
      (lines 3813-3814) run once, before any stream has ever opened -
      nothing can be waiting yet. **One decrement/reset without a
      following `wake_up()` was found**: `px_pcm_sync_stop()`'s own
      timeout/kill recovery path (`atomic_set(&s->in_elapsed, 0)`, added
      in `a92f430`, review round 1) - but this runs *after*
      `wait_event_killable_timeout()` has already returned (by
      definition, since the code is past that call), in the one thread
      that could ever be waiting on this per-stream queue (`sync_stop`
      is not re-entrant for a given substream), so there is no waiter
      left to miss a wakeup here. Not a bug, and not present in the
      hung build either (that `atomic_set()` didn't exist until the
      fix).
   b. **Every `init_waitqueue_head()` call**: exactly two, both in
      `px_probe()` (lines 3815-3816, immediately next to the
      `atomic_set()` inits above), run once per USB device attach.
      Confirmed via the full history of the mechanism (`9490eff` onward)
      that this has never been anywhere else - not in
      `px_start_streaming()`, not in `px_live_apply_restart()`, not
      anywhere a re-init could orphan an already-sleeping waiter.
   c. **Any other path making the condition true without a `wake_up()`**:
      none found. `in_elapsed` is only ever touched by the five sites in
      (a) above; there is no other read-modify path.

Conclusion: the exhaustive check does not find a missing-`wake_up()`,
duplicate-init, or alternate-path bug either. Both this review's
self-deadlock hypothesis and the suggested lost-wakeup hypothesis lack
direct code-level confirmation - the honest position is that the exact
mechanism that left `in_elapsed` stuck remains unresolved from static
analysis (kernel tracing on real hardware would be needed to pin it
further, which is explicitly out of scope right now). What doesn't
change: the fix does not depend on resolving this. `sync_stop`'s wait is
bounded and killable regardless of which lock or which missed wakeup (if
either) turns out to be the real mechanism.

**2. Reschedule removed, replaced with a start-time resync fix.** The
concrete problem with review round 3 item 2's "reschedule once from
`sync_stop`": `px_start_streaming()` runs *synchronously* inside
`prepare()`, before `trigger(START)` can possibly follow it, but a
*rescheduled* work item fires asynchronously, some `LIVE_APPLY_DEBOUNCE_MS`
later - a window in which the application's own `trigger(START)` could
land first, active-flip the stream, and then have the rescheduled
live-apply worker kill the just-submitted URBs out from under it to redo
a restart for the dropped generation. Removed entirely (the
`schedule_delayed_work()` call added at the end of `px_pcm_sync_stop()`
in round 3 is gone).

Replaced with the suggested structural fix: `px_codec_resync_shadow()`
(called from `px_start_streaming()`, before `px->running` is ever set
true, gated by the existing `codec_resync` module param) now snapshots
`px->desired_codec`/`px->desired_gen` under `desired_lock` and replays
*that*, instead of `px->codec`, then sets `px->live_applied_gen` to the
snapshotted generation under `desired_lock` once the replay succeeds.
Since every `px_codec_write()` call (idle-path puts, this resync itself,
and a successful live-apply replay) already mirrors `px->codec` and
`px->desired_codec` together, the two are identical whenever nothing is
pending - this is not a behavior change in the common case, only in the
specific case this round exists to fix: a live-apply generation that was
staged but never committed (aborted mid-flight, or never got the chance
to run) before the stream stopped. No extra work item, no scheduling
delay, no window for `trigger(START)` to race it - the fix is now fully
inside `prepare()`'s own synchronous call. The snapshot is race-free
against a concurrent idle-path put() for the same reason the function's
pre-existing comment already gave (both held off by `px->mutex`, which
`px_pcm_prepare()` holds for this whole call); a concurrent *live-path*
put() isn't reachable here since `px->running` is still false at this
point in the start sequence.

## 13. Phase 3b (2026-10-17): timeline fill across a live-apply restart

Phase 3a (pre3, commit `e79cbef`) is done: live apply works correctly in
REAPER, no hangs, `in_elapsed` balanced across restarts. Its own accepted
tradeoff (section 1: "~0.3s is missing at each toggle") is what phase 3b
exists to remove: a REAPER recording loses ~340ms of real time per toggle
(capture delivers no frames, the playback pointer doesn't move) and
capture/playback drift apart from the application's point of view, even
though nothing is actually broken.

### Design

A single `struct hrtimer fill_timer` (one timer for both streams, since
they are killed/resubmitted together as one group) fabricates frames at
the nominal rate for exactly the stretch between a live-apply restart's
`px_kill_audio_urbs()` and its resubmit:

- **Capture**: writes silence (zero, all `CAP_CHANNELS`) into the ring
  buffer and advances `hwptr`/`period_pos`, exactly like
  `px_cap_complete()` does for real data except with no
  `px_decode_frame()`, no `px_riaa_process_frame()`, no
  `px_cap_update_peaks()` - silence bypasses RIAA entirely (the filter's
  state is untouched, so it resumes from wherever real samples left it,
  not from a zero-input transient) and never writes the peak arrays (a
  ~300ms gap just leaves the last real peak showing).
- **Playback**: advances `hwptr`/`period_pos` with no data copy at all -
  app data in the ring buffer for that stretch is simply discarded, per
  the already-accepted tradeoff that the *device* really does miss
  ~0.3s of real audio during the gap; this phase fixes the *position*
  drift, not the physical gap itself.
- Both reuse the exact `atomic_inc`/`atomic_dec_and_test`/
  `snd_pcm_period_elapsed`/`wake_up` pairing the real completion
  handlers use (`px_play_notify_elapsed()`, and a new
  `px_cap_notify_elapsed()` factored out of `px_cap_complete()` the same
  way) - the fabricated frames balance `in_elapsed` exactly like real
  ones, so this can't reintroduce the review-round-5 leak class.
- A new `px_fill_ms_frames()` (near `px_next_ms_frames()`) drives the
  per-tick frame count, sharing `px->rate_acc` with the real per-URB
  stepping so the fractional carry is exactly where it would have been
  without the gap - deliberately does *not* drain `px->fb_fifo`/
  `fb_count` (no real feedback data arrives during the gap either; using
  stale entries would describe a time they no longer reflect).

**Lifecycle**: `px_fill_start()` (idempotent via `atomic_xchg()`) is
called from `px_live_apply_restart()` right after its own kill - calling
it again on every retry is harmless, only the first call actually arms
the timer, and it then runs continuously across retries with nothing to
restart between them. `px_fill_stop()` (clears `fill_active` *then*
`hrtimer_cancel()`s, so a callback already mid-tick sees the flag false
before deciding whether to re-arm) is called: at the handover point in
both `px_live_apply_restart()` and `px_live_apply_fallback()`, right
before their own real resubmit loop (so the filler and a freshly
resubmitted real URB can never both be advancing the same position);
from `px_live_apply_give_up()` (so the core's own `SNDRV_PCM_POS_XRUN`
handling, review round 5, isn't papered over by a timer that keeps
seamlessly advancing position as if nothing failed); and as
belt-and-braces teardown from `px_pcm_sync_stop()`, `px_stop_streaming()`
and `px_disconnect()`.

**Lock ordering, documented on the callback itself**: `HRTIMER_MODE_REL_SOFT`
means `px_fill_timer_fn()` runs in softirq context - it may take
`cap.lock`/`play.lock` (sequentially, one at a time, never nested
together) but must never do anything that can sleep: no mutex, no
`msleep()`, no `GFP_KERNEL` allocation. `hrtimer_cancel()` itself is only
ever called from process context (the workqueue, or the calling
process's own context for sync_stop/stop_streaming/disconnect), never
from inside the callback, which would deadlock.

**`trigger(STOP)` deliberately does not call `px_fill_stop()` directly** -
it runs in atomic context (the PCM core's own lock, IRQs off), and
`hrtimer_cancel()` can busy-wait for an in-flight softirq callback to
finish; calling it while holding a lock that callback also needs would
be a genuine self-deadlock risk (same class of hazard review round 2
eliminated for `px_live_apply_xrun()`). Not needed anyway: `trigger(STOP)`
already clears `s->active` under `s->lock`, and both `px_fill_capture()`/
`px_fill_playback()` check `s->active` before doing anything - so a
stream that's just been stopped is already a no-op for the filler from
that point on, with the *synchronous* cancel following shortly after
from whichever process-context path (sync_stop, almost always) reaches
it next. Matches this driver's own established pattern for the same
reason (`px_pcm_trigger()`'s existing comment on why the watchdog's
cancel from `trigger(STOP)` is `cancel_delayed_work()`, not `_sync`).

### Acceptance (measured, not assumed - see tests/hw/click_offset.py)

Capture channels 5/6 (the bit-exact internal digital tap of Out 1/2,
`analysis/NOTES.md` "Hardware matrix" - no physical loopback cable
needed) let click position be measured directly against a known
schedule: play a 1-click/s track on Out 1/2, record 6ch, toggle In 1/2
source repeatedly, then check that no click's cumulative drift from a

`tests/hw/click_offset.py` implements this (self-tested against

Full acceptance (hardware, next session): the click-offset test with 5

## 14. Phase 3b review (2026-10-18/19): per-toggle step cause, and a real analysis bug

The 3b acceptance test (pre4) measured systematic per-toggle steps of
3.1-7.8ms (average ~4.4ms), pointing at 1024-frame periods (21.3ms) but
not 256-frame ones (5.3ms). This section instruments the cause on real
hardware (pre5, diagnostic only), implements and verifies a real driver
fix (pre6), and - importantly - finds and fixes a bug in the *test
script itself* that was inflating the apparent problem by roughly 300x
in a follow-up run.

### Instrumentation (pre5)

Added (kept permanently, not stripped - cheap, useful for any future
timing investigation on this path): per-restart counters
(`px->fill_ticks`, `fill_overrun_extra`, `fill_cap_frames`,
`fill_play_frames`), logged in `px_fill_stop()`; `hwptr` snapshots at
kill and at handover, logged in `px_live_apply_restart()`; and a
one-shot "first real completion after a restart" gap measurement
(`px->restart_kill_ns`, `diag_cap_pending`/`diag_play_pending`) in
`px_cap_complete()`/`px_play_complete()`.

**First hypothesis, tested and found wrong**: `hrtimer_forward_now()`
returns the number of periods actually elapsed (confirmed via kernel
docs), and the original code discarded it, always fabricating exactly
one period's worth of frames per callback regardless. On real hardware,
across 9 restarts: `overrun_extra=0` every single time, and the fill
timer's own covered duration matched its tick count to within ~24-100us
over ~307-314ms. This hypothesis is **ruled out** by direct measurement,
not just superseded - the original mechanism (review round 5's commit
message) was wrong about *why* it mattered, even though bounding it
was still correct general hygiene.

**What *was* found, real and driver-side**: a genuinely uncompensated
~1.2-2.9ms gap between `px_fill_stop()` (called right before the real
resubmit, for a clean handover) and the first real completion actually
arriving - during that stretch, neither the timer nor real data advances
position at all. Measured across 9 restarts: capture 1.28-2.9ms,
playback 1.16-1.4ms, every single time, never caught up afterward.

**Fix (pre6)**: `px_fill_catchup_frames()` computes the shortfall -
expected frames from wall-clock time elapsed since the kill
(`px->restart_kill_ns`) minus what the timer actually fabricated
(`fill_cap_frames`/`fill_play_frames`) - and the first real completion
after a restart fabricates exactly that many more frames (reusing
`px_fill_capture()`/`px_fill_playback()` directly) before processing its
own data, so the real data starts from the caught-up position. Verified
on hardware: logged `catchup=` values of 65-138 frames (1.4-2.9ms),
exactly matching `handover_hwptr + catchup == first_completion_hwptr`
in every case checked.

### The analysis bug that made this look far worse

Re-running the 5-toggle click-offset test after the pre6 fix showed
steps that looked like a *severe regression* - near-exactly one full
second lost per toggle, growing cumulatively (worst drift +4.98s by the
end). Investigating *why* (rather than assuming the fix was wrong)
found the real cause: `click_offset.py` indexed every detected click
sequentially (`expected = t0 + i * period`) and had no way to represent
"a click was missing." A live-apply restart's ~310ms gap can coincide
with the exact moment a click should have played - replacing it with
real silence, a genuine, one-time loss of audio (not a position
error) - and when that happens, the detector simply never sees that
one click, so every click *after* it was off by a full index, which the
old script's cumulative-drift math misread as 1 full second of
permanent drift. Confirmed directly: `np.diff(click_times)` showed
exactly one 1.9966s interval per toggle, immediately followed by a
clean, exact 1.0000s cadence for the rest of the recording - the
*position tracking* was fine throughout; the script's bookkeeping
wasn't.

Fixed `click_offset.py` to advance its expected-schedule index by the
*rounded* number of periods actually elapsed between consecutive
detected clicks, not always by 1 - this correctly separates "N clicks
missing" (reported separately, not as drift) from genuine sub-period
timing error. Re-running the pre6 capture through the corrected script:

| toggle | step (pre4, original) | step (pre6, corrected analysis) |
|---|---|---|
| 1 | 3.1ms | 3.4ms |
| 2 | 4.0ms | 3.5ms |
| 3 | 3.7ms | 3.3ms |
| 4 | 3.3ms | 3.6ms |
| 5 | 7.8ms | 6.8ms |

**The pre6 fix made a real, verified, small improvement (closing the
1.2-2.9ms handover-tail gap) but did not meaningfully change the
dominant per-toggle step** - the corrected numbers are within noise of
the original ones. One click is genuinely lost per toggle in both
builds (confirmed separately, correctly reported by the fixed script
as "N click(s) missed here", not conflated with drift).

### Cause: (b), device-side - with the evidence the task asked for

The task's own test for (b) was "the same driver frame counts on both
sides but a shifted click" - that is exactly what was found:
`fill_cap_frames == fill_play_frames` on every single restart (the
timer fabricates identical frame counts for both streams, confirmed
exact), and the handover-tail gap (now compensated) was shown to be a
minor (1-3ms) contributor, not the dominant one - yet a ~3.3-6.8ms click
shift remains, at every restart, correlating with neither gap duration
nor any driver-measured quantity:

- Gap duration (fill-covered) ranged 307.2-312.0ms across the 9
  instrumented restarts, uncorrelated with the drift step
  (longest gap, restart 3 at 312.0ms, had one of the *smaller* steps;
  shortest gap, restart 5 at 307.2ms, had the *largest*).
- The drift **accumulates** across toggles rather than appearing once
  and staying constant - consistent with each restart's own USB
  resubmission landing at a slightly different micro-frame phase
  (not controlled by this driver, an artifact of exactly when the
  resubmit's first isochronous packet happens to be scheduled), which
  plausibly shifts the device's own playback DAC FIFO prefill by a
  small amount each time - not with a fixed, deterministic rounding
  bug in this driver's own frame accounting, which has now been checked
  twice (reviews round 5 and this one) and found exact both times.

**Compensation feasibility: low.** The magnitude varies run to run
(3.3-6.8ms here, not a fixed constant), which rules out a static
software offset correction. A dynamic one would need a live reference
signal to measure the actual shift after *each* restart, which doesn't
exist outside this specific click-track test - normal use has no such
reference. Not implemented; flagged as a hardware characteristic to
document, not a driver bug to chase further.

### Separately confirmed: one click genuinely lost per restart

Independent of any drift question: a live-apply restart's ~310ms gap,
when it coincides with a transient event's exact timing (here, a

it was never claimed to recover content lost *during* it). Worth
knowing for REAPER sessions with percussive/transient content specifically
(not sustained material), where a toggle landing exactly on a transient
could audibly drop it.

## 15. Review round 2 (2026-10-19): the step is deterministic, not device jitter - found and fixed

Section 14 concluded hypothesis (b) (device-side) based on the step not
correlating with gap duration. That conclusion was wrong, and caught by
a sharper read of the same data: **every step had the same sign and
accumulated monotonically** (never reversing) - random device jitter
would scatter around zero, not drift one direction forever. That is the
signature of a deterministic driver bug.

### The bug: playback prefill double-counts against the timer's own advance

`px_live_apply_restart()`/`fallback()` prefill each resubmitted playback
URB (`px_fill_play_urb()`) before resubmitting it - this advances
`play.hwptr`/`period_pos` by that URB's own frame count, same as any
steady-state refill. Instrumented directly: **exactly 192 frames
(`PLAY_URBS` x 48 nominal frames at 48kHz) on every single restart
measured, zero variance** (20 restarts across two test sessions). The
fill timer already advances `play.hwptr` continuously across the whole
gap to maintain wall-clock continuity (section 13's whole point) - the
prefill's own 192-frame advance lands *on top* of that, re-establishing
a fresh "pipeline depth" that adds to whatever depth already existed
from before the restart, rather than replacing it. Each restart adds
another ~192 frames that nothing ever removes - exactly the accumulation
observed.

### First fix attempt: subtract the prefill from the catch-up (pre8) - still didn't help

Added `px->play_prefill_frames` and subtracted it from the existing
handover catch-up's target. On hardware, this made no measurable
difference: logged `catchup=0` on every single one of 10 restarts - the
clamped-at-zero `px_fill_catchup_frames()` was discarding a *negative*
correction the position genuinely needed (fabricated + prefill already
exceeded the wall-clock target every time), silently doing nothing.

### Second fix attempt: allow the correction to go negative (pre9) - mathematically exact, but unsafe

Added a signed `px_fill_catchup_delta()` and a `px_fill_playback_rewind()`
to apply negative corrections. The math was verified exact (total
advance matched wall-clock-expected to under 1 frame on every restart).
But on hardware, this introduced a new, serious problem: `play.hwptr` is
reported directly to the ALSA core via `.pointer()`, which requires
monotonic (forward-only, circular) position reporting - moving it
backward, even by a small amount, corrupts the core's own tracking
whenever that backward move happens to cross a buffer wrap. Confirmed
on hardware: two of ten restarts (both ones where the rewind landed
`play.hwptr` at a low value right after a prefill-induced wrap) produced
a spurious full-scale transient roughly one buffer-length (500ms, this
test's buffer size) after a real click - traced and confirmed absent
from the source click-track file, so genuinely introduced by this
rewind, not a coincidence or a detector artifact. This would have been
an audible glitch in real use. Caught before trusting the approach,
reverted.

### Third fix (pre10): reserve the prefill's own size, never move hwptr backward

The actual fix: `px->play_fill_reserve`, set to the prefill's known,
constant size (`PLAY_URBS * (px->rate / 1000)` - exact for this device,
since the feedback FIFO the same frame-count function would otherwise
consult is always empty at this exact point, the feedback URBs having
just been killed and resubmitted alongside it with no time for real
data to arrive) at `px_fill_start()`. `px_fill_timer_fn()` withholds
exactly that many frames of its own *playback* advance up front (via
`px_fill_playback_reserved()`) before playback filling begins - capture
is unaffected, filling normally from the first tick, since it has no
prefill step to reserve room for. By the time the prefill actually runs,
the timer's playback total is already short of wall-clock by roughly the
prefill's own size, so the prefill's addition completes it instead of
overshooting it - and the existing (now-always-small, always-positive)
handover catch-up closes the small remainder, exactly as it always did
for capture. Every operation here is forward-only; `play.hwptr` never
decreases anywhere in the driver.

### The `px_fill_stop()` stale-counter bug

One log line looked alarming on first read: `fill timer: 307 ticks over
700230786us` (700+ *seconds*, at a `pcm close` 12 minutes after the
restart that actually produced those 307 ticks). Traced via
`journalctl -k` back to that restart (gen=10, from this session's own
earlier pre10 verification, not the user's REAPER run): it committed
cleanly, normal handover, no abort. **No data corruption** - the fill
timer was not stuck.

Root cause: `px_fill_stop()`'s diagnostic log was gated on
`if (px->fill_ticks)`, but `fill_ticks` is only ever *reset* by
`px_fill_start()`, never cleared by a stop. Every subsequent
belt-and-braces `px_fill_stop()` call on an already-stopped timer (one
fires on every `sync_stop`/`stop_streaming`/`disconnect`, whether or not
the timer is actually still running) re-logged the same stale counters
and a bogus elapsed time computed against a `fill_start_ns` from
whichever restart happened to run last, however long ago. Fixed: gate
the log on `atomic_xchg(&px->fill_active, 0)`'s own return value
(`was_active`) instead - true only on the call that actually transitions
the timer from running to stopped.

### Item 2: does the prefill reservation apply on the fallback path, and after a retry?

**Fallback path**: yes, identically. `px_live_apply_fallback()`'s own
resubmit loop is byte-for-byte the same pattern as
`px_live_apply_restart()`'s - `px_fill_stop()`, then the PLAY_URBS loop
measuring `prefill_frames` from a before/after `hwptr` snapshot into
`px->play_prefill_frames`, consumed the same way by
`px_play_complete()`'s catch-up. No separate accounting needed because
there's only ever one piece of state (`play_fill_reserve`/
`play_prefill_frames`) and both paths feed it the same way.

**Retries**: also correct, for a reason that falls out of two existing
properties rather than needing new code: `px_fill_start()` is idempotent
(`atomic_xchg`) and only resets `play_fill_reserve` on an actual 0->1
transition, so the *same* reserve set by the first attempt persists
across however many retries follow within one restart sequence; and the
192-frame reserve is always fully consumed by the timer within the
first ~4ms, far shorter than any realistic attempt duration (each
attempt's own settle sleep alone is 170-500ms), so by the time *any*
attempt's handover/prefill actually runs, the reserve is already 0 and
the mechanism is correct regardless of which attempt that was.

**One real, narrow gap found and fixed**: if `usb_submit_urb()` itself
fails partway through the PLAY_URBS loop (not reachable via the
existing `live_fail_step=5` fault injection, which fails *before* that
loop starts - only a genuine submission failure, e.g. under resource
exhaustion, reaches this), the URBs submitted before the failing one
already had `px_fill_play_urb()` advance `play.hwptr` for them - a
phantom advance that never actually plays (those URBs get killed again
before transmitting). The `fail:` path didn't account for this partial
advance, so a subsequent retry's fresh 192-frame reserve wouldn't know
part of it had already been "spent" - a bounded (<=144 frames, ~3ms),
one-time, non-accumulating double-count, never exercised by the current
fault-injection test matrix.

Fixed with the same forward-only philosophy as the main fix: a new
`px->play_fill_carry` field, set by `px_live_apply_restart()`'s `fail:`
path to whatever partial advance already happened, consumed (subtracted
from the fresh reserve, then cleared) by the very next
`px_fill_start()` - which is always the next retry's own, since that is
the only path that calls `px_live_apply_restart()`'s `fail:` and then
tries again. See `phasex64.c`'s `play_fill_carry` field comment,
`px_fill_start()`, and `px_live_apply_restart()`'s `fail:` label.

Deliberately **not** added to `px_live_apply_fallback()`'s own `fail:`
path: that function is always the *last* attempt (`px_live_apply_work()`
calls it exactly once, after every restart retry is exhausted), so a
failure there goes straight to `px_live_apply_give_up()`, never another
`px_fill_start()` - there is no next attempt to carry anything forward
to, and any phantom advance is moot once the stream is handed to the
core's XRUN recovery (the next genuine start goes through
`px_pcm_prepare()`, which resets `play.hwptr` fresh regardless of this
field).

**Abort/give-up paths confirmed clean**: `px_live_apply_give_up()` now
also clears `play_fill_carry` defensively (belt-and-braces - no current
path leaves it nonzero there, but a stray value must never bleed into a
future, unrelated stream's first live-apply restart). `play_fill_reserve`
itself needs no equivalent clear: `px_fill_start()` always resets it
unconditionally on every real 0->1 transition, and nothing reads it
between a give-up and the next start (`px_pcm_prepare()`/
`px_start_streaming()` don't touch the filler at all).

## 17. v0.1.12 release summary

**What live apply does**: a codec/routing change made while a stream is
running applies live, without stopping playback/capture. The ~300-340ms
gap between killing the old URBs and the new ones going live is filled
with fabricated frames (silence for capture, position-advance-only for
playback) so the stream's timeline position stays continuous - a REAPER
recording's length and sample positions are unaffected by a toggle, with
measured drift **under 3ms per toggle, not accumulating** across a
session (10-toggle hardware run: -2.6ms to +2.2ms total, 8/10 toggles
under 1ms - see section 15). Before v0.1.12, the same change only took
effect at the next stream start.

**Known limits**:
- One click/transient that happens to land exactly in the ~0.3s gap can
  be lost (replaced by silence) - this is a one-time, bounded event, not
  drift, and is by design: filling the gap with fabricated real audio
  would require predicting content that hasn't happened yet.
- Audio is genuinely unavailable for ~0.3s during the toggle itself -
  this is the live-apply mechanism's own cost (URBs must be killed and
  the device reconfigured), not something phase 3b changes; phase 3b's
  job is only to keep the *timeline* continuous across that gap, not to
  avoid it.
